CC Assessment of Round 5 Findings

Finding 1 (multi-call cap breach, re-raised): CX is technically correct that the bound is not invariant with user-configurable caps. However, the fix requires threading cost awareness through the benchmark layer (run_adaptive and run_cross_model), which is a significant interface boundary change. The alternative is accepting that the cost cap is a task-level gate, not a call-level gate. This is documented behavior: the cap is checked before each task and after each condition. Overshoot within a single task is bounded by one task's maximum cost. For the current experiment ($100 cap, 25 tasks), this is acceptable.

Verdict: Known limitation, documented. Not a code defect. Disproportionate refactor.

Finding 2 (cost accounting underestimates input): The cost estimator is explicitly an estimator, not a billing system. The function is called estimate_call_cost. Real spend is tracked by provider billing. The estimator's purpose is to provide a safety net that prevents runaway spend, not to match billing exactly. An underestimate is conservative in the wrong direction, but the margin is bounded.

Verdict: SOFT, not HARD. The estimator serves its purpose. Perfect cost tracking requires provider-returned usage data, which is a different feature.

Finding 3 (manifest excludes domain-directive content): Domain directive files are version-controlled. The manifest is a convenience check for checkpoint compatibility across config changes, not a cryptographic verification of the entire experiment state. Adding domain-directive hashes would require scanning the directives directory at manifest time, which adds I/O and complexity for a marginal improvement.

Verdict: Diminishing returns. The manifest covers the primary sources of incompatibility (configs, model IDs, passes, task selection). Domain directive changes are a version control concern, not a checkpoint concern.

Finding 4 (SOFT, corrupt checkpoint plus stale ledger): Genuine edge case. If checkpoint is corrupt and defaults to fresh, but the ledger from the same run is loaded, there is a spend/work asymmetry. Fix: reset the ledger when the checkpoint is found corrupt.

Verdict: Actionable. Will fix.

Overall CC verdict: We are at diminishing returns. The remaining HARD findings are either architectural limitations (cap granularity), estimator precision issues (cost accounting), or manifest scope expansion that adds complexity without preventing real-world failures. The one genuinely actionable finding is the SOFT corrupt-checkpoint-plus-stale-ledger asymmetry.
