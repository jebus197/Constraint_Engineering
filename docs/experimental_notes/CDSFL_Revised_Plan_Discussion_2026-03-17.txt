CDSFL Revised Experiment Plan, Full Discussion and P-Pass Results

Date: 17 March 2026

This document covers the full breakdown of the revised CDSFL experimental plan, why it was revised, what the P-pass found wrong with the original design, and what the corrected plan involves.


THE PROBLEM WITH THE ORIGINAL PLAN

The original experiment, which is still running as Phase 1, plants known faults in constrained STEM problems and asks models to find them. The results so far show 90 to 100 percent detection rates even without CDSFL. This means the tasks are too easy for frontier models, and the maximum improvement CDSFL can show is compressed to 0 to 10 percentage points.

This is a floor test, not a ceiling test. CDSFL was designed to break the frontier window, meaning it should help most when models are working at the limits of their capability, on novel problems where there is no pre-existing answer key, and where errors are emergent rather than planted.

The original plan proposed a Phase 2 to fix this, but when I ran a P-pass against my own Phase 2 design, I found several serious problems.


WHAT THE P-PASS FOUND (5 Passes Against the Plan)

Pass 1, Structural Soundness.

First, expert blind evaluation is infeasible at this scale. The plan called for domain experts to score final outputs. But 25 tasks multiplied by 3 schemas multiplied by 7 models gives 525 outputs. George is one person and cannot blind-evaluate hundreds of technical outputs across 10 domains.

Second, the per-pass delta measurement had no concrete methodology. The plan said to track what each pass found that the previous pass missed, but did not specify how to compute this comparison. Human scoring does not scale. Using a language model as judge is circular if it is the same model being evaluated. Automated text diffing misses semantic meaning.

Third, who designs the 25 frontier tasks? If I design them, they carry my biases. If George designs them, he would need domain expertise across all 10 domains. Neither is ideal. Task design is the hardest unsolved problem in the plan.

Pass 2, Schema Applicability.

Fourth, Schema B, the modular 4 plus 1 schema, requires tasks with 3 or more distinct modules with independent constraint sets. Not all frontier tasks are naturally modular. The plan implied all schemas apply to all tasks, but they do not.

Fifth, Schema C, the cross-model adversarial schema, is underspecified and costs 3 times as much as Schema A. It needs 3 different models per task at 5 passes each, giving 15 API calls per task versus 5 for Schema A. But the plan did not specify which model pairs to use.

Sixth, Schema A's description contradicted the P-pass protocol. The plan said Pass 2 uses a fresh context, but the actual P-pass protocol from CLAUDE dot MD is iterative, where each pass builds on prior findings. These are two different experimental conditions and the plan conflated them.

Pass 3, The Fundamental Measurement Problem.

Seventh, and most severe: Phase 2 has no ground truth. Phase 1 works because planted faults have known correct answers. Phase 2 deliberately removes this. Without ground truth, improvement becomes a judgment call rather than a measurement.

The resolution is to use tasks where correctness is objectively verifiable even though faults are not pre-planted. Mathematical proofs that can be machine-checked. Code solutions that must pass a test suite. Engineering designs that must satisfy quantifiable physical constraints. Chemical syntheses that must obey conservation laws. You do not need to pre-plant faults if you can verify outputs. The faults reveal themselves through verification.

Pass 4, Confounds and Controls.

Eighth, there is a prompt-length confound. CDSFL prompts are longer than control prompts. Some improvement might come from prompt quality, meaning better instructions, rather than from the falsification methodology itself. To control for this, we need a placebo condition with equally long but non-CDSFL prompts, such as generic "be careful, check your work, think step by step" instructions of similar length. Without this control, a critic can dismiss any CDSFL improvement as just better prompting.

Ninth, the scale is enormous without scoping. 7 models times 3 schemas times 25 tasks times 5 passes gives 2625 API calls. This needs a core set of 3 to 4 models for full testing and an extended set for selective validation.

Pass 5, What is Missing.

Tenth, the plan ignores Genesis case-study evidence. George has months of documented CDSFL usage where the framework caught real errors. CX finding test design flaws, constitution issues, and so on. This is legitimate case-study evidence and should be presented as complementary data.

Eleventh, adaptive termination needs an algorithm. Diminishing returns is vague. Concrete proposal: if pass N produces zero findings categorised as moderate or severe, terminate. Maximum 5 passes regardless.

Twelfth, diminishing returns from this P-pass itself reached. Stopping.


WHAT THE REVISED PLAN LOOKS LIKE

Three phases remain. Phase 1 is the floor test, already running. Phase 2 is the ceiling test, redesigned. Phase 3 is adversarial review with CX.

Phase 2 changes:

One. Tasks must be verifiable, not just hard. The key design criterion is that correctness can be checked after the model responds, without pre-planting faults. Five categories: proof tasks that are machine-checkable, code tasks that must pass test suites, design tasks with quantifiable constraints, synthesis tasks obeying physical laws, and reasoning-about-reasoning tasks where internal consistency is the ground truth.

Two. Scoring uses verification, not expert judgment. Proofs are machine-checkable. Code solutions get test suites. Designs have computable constraint satisfaction. This makes scoring objective and scalable.

Three. A placebo control condition is added. Three conditions per task: bare prompt as control, full CDSFL with P-passes, and a placebo with equally long generic instructions and the same number of passes but without CDSFL's specific falsification method. If CDSFL beats placebo, the improvement is from the method, not just from longer prompting. This is the control that makes the experiment resistant to the most obvious criticism.

Four. Schema applicability is per-task, not universal. Schema A, the monolithic 5-pass, applies to all tasks. Schema B, the modular 4 plus 1, applies only to tasks with 3 or more identifiable subsystems, tagged at design time. Schema C, cross-model adversarial, is applied to a representative subset of about 10 of 25 tasks with 3 model pairs chosen to maximise training-bias diversity.

Five. Core versus extended model split. Core models for full testing: Sonnet 4 with thinking, GPT-4o, and Gemini Pro. One reasoning-capable model per provider family, maximum diversity. Extended models for validation only: Sonnet 4 standard, o3-mini, Gemini Flash, and Llama 3.3.

Six. Adaptive termination algorithm. Pass N terminates if it produces zero findings categorised as moderate or severe. Maximum 5 passes regardless.

Seven. A Genesis case-study appendix documenting 5 to 10 specific real-world instances where CDSFL caught genuine errors.


REVISED COST ESTIMATE

Phase 2 revised scope: approximately 1875 API calls total. Estimated cost 50 to 80 pounds at frontier model pricing. Phase 1 cost so far approximately 15 pounds.


THE THREE P-PASS SCHEMAS EXPLAINED

Schema A, Standard Monolithic. The model generates a solution in pass 1. In passes 2 through 5, it iteratively falsifies its own output, each pass building on the findings of the previous pass. The full prior chain is visible. This tests whether structured iterative self-checking improves output quality.

Schema B, Extended Modular. For problems with 3 or more distinct subsystems. Passes 1 through 4 each focus on one module in isolation, falsifying that module's constraints, interfaces, and assumptions. Pass 5 runs in a completely isolated context with only the original problem and the current draft, using the adversarial brief. No prior P-pass analyses are visible. This tests whether modular decomposition plus isolated adversarial review outperforms monolithic self-checking.

Schema C, Cross-Model Adversarial. Model A generates the solution. Model B falsifies it. Model A responds to the findings. Model B re-checks. A third model or fresh instance runs the isolated adversarial pass. This tests whether epistemic friction between models with different training biases produces better falsification than self-checking.

The hypothesis: Schema C should produce the strongest results because different models have different blind spots. Schema B should outperform Schema A on modular problems because isolation prevents anchoring on prior conclusions. Schema A is the baseline for comparison.
