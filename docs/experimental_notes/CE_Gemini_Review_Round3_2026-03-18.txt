1. SCIENTIFIC VALIDITY: The "History Deletion" Confound (Standard vs. Extended)

There is a fundamental structural difference between run_experimental (Standard) and run_extended (Extended) that invalidates them as a clean comparison of "context isolation."

Standard Mode: Every pass (via FOLLOWUP_PASS_TEMPLATE) explicitly receives the prior_issues. The model is told: "Issues identified on the previous pass: {prior_issues}".

Extended Mode: The final adversarial pass (via ADVERSARIAL_PASS_TEMPLATE) deletes the issue history. It only receives the current_draft and the original task_prompt.

The Flaw: Any performance delta in "Extended" mode cannot be strictly attributed to "fresh context" (isolation). It is confounded by "history deletion." If the previous pass produced "hallucinated" issues that distracted the model, Extended mode will perform better simply because it isn't distracted, not because of isolation. This makes the "isolation" metric scientifically uninterpretable.

2. RESULT CORRUPTION: Draft-to-Metadata "Catastrophic Feedback"

In run_benchmark.py, both run_experimental and run_extended employ a dangerous fallback when the model fails to follow the section formatting:

current_draft = extracted_revision or response

The Failure: If a model produces ISSUES_FOUND but omits the REVISED_ANSWER section (e.g., if it concludes no changes are needed), the current_draft for the next pass becomes the entire raw response (including the "ISSUES_FOUND" header and the list of problems).

The Corruption: In the next pass, the model is asked to "attack and revise" a draft that is now 50% metadata. The model will begin "fixing" the ISSUES_FOUND header or incorporating the metadata into the actual answer. The benchmark is no longer measuring the task; it is measuring the model's reaction to its own corrupted state.

3. SECURITY: Template-Injection Denial of Service (DoS)

The harness uses Python's .format() method to inject task["prompt"] and model-generated drafts directly into templates.

The Vulnerability: Task prompts or model-generated drafts containing curly braces {} will trigger a KeyError or ValueError in the Python interpreter.

The Exploit: A malicious (or merely complex) task file with a prompt like "Given the set {x, y}..." will crash the entire benchmark run instantly. Because run_phase2.py does not wrap the main loop's format calls in task-level exception handling, a single { anywhere in the input/output stream is a "poison pill" that kills the multi-hour process.

4. RESULT CORRUPTION: "Ghosting" in Phase 2 Completion Reports

The reporting logic at the end of run_phase2.py is architecturally "blind" to missing tasks.

The Logic: The report generator iterates through checkpoint.completed.items(). It counts RESOLVED and DEFERRED items found in the checkpoint.

The Problem: If the benchmark was interrupted (e.g., by a 429 error) and 50 out of 100 tasks are missing from the checkpoint, the report will still show a "clean" summary: "RESOLVED: 45, DEFERRED: 5".

The Impact: A researcher looking at the deferred_for_review.json would conclude the run was successful and 100% of tasks were accounted for, when in fact half the data is missing. The report fails to compare the checkpoint count against the task_count from the manifest.
