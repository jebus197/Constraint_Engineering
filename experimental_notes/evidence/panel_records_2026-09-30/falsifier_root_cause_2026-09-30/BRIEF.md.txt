### The 4 questions, in the founder's own terms

**Q1 — IS THERE A ROOT CAUSE, AND IS IT FIXABLE WITHIN SPEC?** A candidate hypothesis is offered so you can attack it, not adopt it: that seats are never shown the one proven pattern this project has for falsifying a claim stated in prose, and that `UNTOOLABLE` is an available qualitative escape hatch. Supporting evidence, each to be re-verified: the fixture corpus above is unreachable from the live path; the project has measured that **28 of 28** findings carrying `UNTOOLABLE` were in fact toolable; and the standing rule `feedback_no_qualitative_escape` records that models default to natural-language reasoning whenever a directive permits it. **Against that hypothesis:** teaching was already tested on 2026-06-07 and returned **1 of 3** against 0 of 5 untaught, recorded as *"a marginal booster, not a cure"* because models do not learn across calls, while capability-aware ROUTING reached **7 of 7** on the same residuals. So if the answer were only "teach the pattern", that measurement predicts it will underperform routing. Decide whether the root cause is absent instruction, absent routing, absent capability, or something none of these names.

**Q2 — PROSE TARGETS, AND WHETHER A NATURAL-LANGUAGE QUESTION CAN STILL BE COMPUTABLE.** The founder's original framing, verbatim: *"look at a body of prose and decide if it contained computationally admissible elements? Such as a maths problem, a chemical equation, a line of code etc. If it did it would be considered admissible and solvable ... while allowing the models to use their innate intelligence first and using tools to verify/falsify any assumptions they make. If it contained no computable elements then it would be listed as inadmissible."* He asks whether the lessons since have been applied. He then raises a distinct case: *"There may be a case where a question could be posed fully in natural language, but that could nevertheless be theoretically computable."* His example is the Wolfram connector, which takes natural language and returns computed output. His question: *"Is there nothing we can learn from this, or could apply in our case, or is our only option to offer this facility when a user may have the Wolfram Connector resource installed — which would then unfortunately limit us to this and to natural language maths problems, rather than STEM more generally?"* **THE WOLFRAM CONSTRAINT, CORRECTED BEFORE YOU REASON FROM IT. An earlier draft of this brief stated a rule that does not exist, and the founder caught it.** That draft said a STORED falsifier may not call Wolfram, and attributed it to him. It is not his ruling. It is an inference, and `.claude/CLAUDE.md:251` compounds the error by calling it *"the founder's own condition rather than a preference"*. This is the second Wolfram rule in 2 days that acquired his name without his words behind it; see `feedback_rejected_advice_acquires_authority`.

**His actual ruling, verbatim, 2026-09-28, and note that its emphasis is the opposite of the draft's:** *"you appear to be potentially overstating a user preference as a 'rule'. But if it is to be a rule that rule stated plainly should be that no user should be compelled to use Wolfram before they can run an experiment, but that anyone running the project should be offered the opportunity to install it via onboarding.md, in the same 'best of both' configuration discussed here. And where available to whatever orchestrator model they might load it with, that model should adopt the rule to use this configuration whenever available, or default to other tools such as SymPy -- and the other STEM Open Source tools listed in your local and global CLAUDE.md files, which should also be made available to them to install by running onboarding.md. ... Wolfram (when available) however should remain the secondary falsifier ran against any output produced from the installed Open Source tools and should never be considered the primary falsifier route."*

**So the binding rule is: nobody is COMPELLED to install Wolfram; where it IS available the model SHOULD use it, as a SECONDARY falsifier against open-source output, never primary.** Nothing in that forbids a stored falsifier from calling it.

**WHETHER A STORED FALSIFIER MAY CALL WOLFRAM IS THEREFORE AN OPEN QUESTION, AND IT IS PART OF Q2.** The refusal is live in code at `bench/falsifier_verify.py:596`, which raises `PermissionError("Wolfram refused")` on any scored falsifier that reaches for the kernel. Its 2 stated reasons are technical and worth weighing on their merits rather than dismissing: a falsifier must re-run on a machine that has no Wolfram, and falsifiers run in parallel against 1 licensed kernel. Measured: **0 of 1,006 archived falsifier sources mention Wolfram**, so the refusal has never actually bitten. Decide whether it should stand, and if it should, say so as an engineering judgement rather than as his ruling.

**The capability limit is separate and is measured.** On 2026-09-29 a headless `claude -p` seat saw **0** MCP tools whose name contains "olfram", so the natural-language connector route is unreachable from a command-line seat regardless of policy. His question is whether anything about that natural-language capability can be reproduced with the open-source set, or whether offering it only to users who have installed Wolfram would confine the project to natural-language mathematics rather than STEM generally.
