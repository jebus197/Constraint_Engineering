## THE STANDARD YOU ARE JUDGING AGAINST — read this before anything else

The founder was explicit that "simplest sufficient" is a FORMAL term here, not a
casual one, and that you must understand it before being asked to apply it. From
the project's own record:

  * Default to the simplest sufficient solution.
  * **Before building a mechanism, state what would go wrong if it did not exist,
    and check whether some cheaper property already prevents that.**
  * **Prefer extending machinery that exists and is already trusted over inventing
    a new component.**
  * When several attempts at a solution all fail, treat that as evidence the
    problem is MIS-FRAMED, not licence to escalate to a heavier tool.
  * The origin case: a fix needed a "splitter" to answer "is this a NEW defect?".
    The real requirement was "is this UNRESOLVED?" — trivial, already answered by
    the registry. The hard question never needed answering.

So for each fix below, answer three things:
  (a) Is it SOUND — does it do what it claims, verified by execution?
  (b) Is it SIMPLEST SUFFICIENT — or does a cheaper existing property already
      achieve it? Name that property if so.
  (c) If either answer is no, SUPPLY THE FIX. A finding without a repair is half
      an answer here. If a fix is sound and minimal, say so in one line and move on.
      Do not manufacture faults.

Run things. Assertions about source text are not evidence in this project.
Budget 30 minutes. Two well-executed judgements beat a survey.

**Attack:**
