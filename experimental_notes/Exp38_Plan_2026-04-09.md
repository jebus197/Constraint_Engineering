## 2. Mathematical Model Updates (S_k Extension)

### 2.1 S_k Replaces Model-Estimated sigma

The current operational directive uses σ (sigma, solution efficacy) as a model-estimated probability. This is replaced by S_k (the tool-verified solution-reliability score):

```
S_k = A * E

where:
  A = product of all hard gates (binary: 0 or 1)
  E = weighted aggregate of all effect evidence scores (graded: [0, 1])
```

A single hard gate failure zeros the entire fix. Effect evidence is graded and aggregated with domain-specific weights.

### 2.2 Bounded nu_eff (Re-injection)

Re-injection (the introduction of new defects when a fix is applied) is split into baseline (nu_b, the rate from any modification) and fix-induced (nu_f, the additional rate from a flawed fix):

```
nu_eff = 1 - (1 - nu_b) * (1 - (1 - S) * nu_f)

Expands to: nu_eff = nu_b + nu_f - nu_b * nu_f - S * nu_f * (1 - nu_b)
```

Properties:
- S=0 (fix failed): nu_eff = nu_b + nu_f - nu_b*nu_f (maximum, bounded in [0,1])
- S=1 (fix perfect): nu_eff = nu_b (baseline only)
- Automatically stays in [0,1] without clamping
- Difference from linear (nu_b + (1-S)*nu_f) is O(nu_b * nu_f), typically ~0.03

### 2.3 HARD Constraint: nu_b + nu_f <= 1

Both models independently identified this missing constraint. Without it, the linear form can produce nu_eff > 1. The bounded form handles this automatically but the constraint should be stated explicitly as a validity condition.

### 2.4 R_k Update (Complete Equation)

```
Phase 1 — Detection:  q = eta * d * p
                       R_det = R_old * (1 - q) / (1 - q * R_old)

Phase 2 — Resolution:  R_base = S_k * R_det + (1 - S_k) * R_old

Phase 3 — Re-injection: R_k = R_base * (1 - nu_eff) + nu_eff
```

### 2.5 S* Break-Even Threshold

Fixes below S* (the break-even threshold) do more harm than good (the Valley of Bad Fixes — an emergent regime where partially correct fixes increase total risk):

```
Linear:   S* = (nu_b + nu_f - q*R) / nu_f
Bounded:  S* = (nu_b + nu_f - nu_b*nu_f - q*R) / (nu_f * (1 - nu_b))
```

R_new(S) is a downward-opening parabola. Intermediate S values can INCREASE risk above baseline. The S* gate rejects fixes below the break-even threshold.

**Dual formulation (ν\*):** The break-even can also be expressed as the maximum
tolerable re-injection rate for a given fix quality:
```
ν* = S_k · R · q / (1 - q · R · (1 - S_k))
```
S* and ν* are algebraic duals. The runner implements S* (operational: "is this fix
good enough?"). ν* is available for analytical use ("how much re-injection can I
tolerate?") but is not separately computed in the pipeline.

### 2.6 Multi-Model Aggregation

For panels with multiple models proposing fixes:

```
Detection:    q_eff = 1 - product_m(1 - rho_m * q_m)
              where rho_m is inter-model correlation coefficient

Fix selection: S_panel = max(S_k) across models (max-pooling)
```

### 2.7 Composed Model Layers

Five independent layers that compose without conflict:
1. S_k computation (A * E from tool gates)
2. nu_eff computation (bounded form)
3. Fix format (SEARCH/REPLACE blocks)
4. Multi-model aggregation (correlation-adjusted q_eff + max-pooling)
5. S* threshold gate (reject below break-even)

## 3. Template Fixes (Mandatory Before Exp 38 Runs)

### 3.1 E Aggregation Formula

**Bug:** Any e_i = 0 collapses the entire E term to zero under product/geometric mean. This destroys graded semantics.

**Fix (APPLIED):** Weighted arithmetic mean over applicable gates only:

```
E = sum((w_i / W) * e_i)  where W = sum(w_i) over applicable gates only
```

Skipped gates (not applicable) are excluded from the sum AND from the weight denominator. A single zero-score gate reduces E proportionally rather than vetoing it entirely — if a gate is genuinely non-negotiable, it belongs in the hard gates (A), not in effect evidence. Unavailable gates (tool not found, tool crashed) return None and are excluded; if ALL effect gates are unavailable, tristate is ESCALATE.

Design choice resolved: arithmetic mean selected over geometric mean. Geometric mean gives any single gate veto power (e_i=0 → E=0), destroying the architectural separation between A (admissibility/veto) and E (graded quality). Arithmetic mean preserves graded semantics.

### 3.2 Baseline Semantics

**Bug:** Delta-from-baseline is used throughout but never formally defined.

**Fix:** Add first-class section to template:

```
BASELINE CAPTURE:
  When: Immediately before fix application
  What: Run all gates against the unmodified artifact
  Store: gate_id -> baseline_score for each gate
  Delta: gate_score_after_fix - baseline_score
  Policy: Only NEW failures count. Pre-existing failures excluded.
```

### 3.3 Applicability/Skip Rules

**Bug:** When a gate does not apply to a domain (no type checker in chemistry, no stoichiometric balance in code), behaviour is undefined.

**Fix:** Renormalise weights over applicable gates only. Non-applicable gates are removed from both the product and the weight denominator. When NO graded gates apply, E defaults to 1.0 (the fix is admissible but ungraded — ESCALATE for human review if warranted).

### 3.4 Tristate Architecture

**Extension:** Replace binary S_k/zero with three states:

```
ADMISSIBLE:  S_k > S* and all hard gates pass. Fix is accepted.
REJECTED:    Any hard gate fails OR S_k < S*. Fix is rejected.
ESCALATE:    Required evidence is genuinely unavailable (tools don't exist
             for this domain/gate). Distinct from "fix failed" — the system
             honestly reports it cannot determine the answer.
```

ESCALATE preserves the numeric S_k for gates that CAN be evaluated and flags the boundary between verified and unverifiable.

## 4. Python Gate Corrections

### 4.1 g2: Import Resolution -> py_compile

**Bug:** `import <module>` is too brittle. Side-effectful imports, missing environment variables, and optional dependencies cause false vetoes.

**Fix:** Replace with `py_compile.compile(source)` which checks syntax without executing imports. Rename to "Compilation Check."

### 4.2 g3: mypy Conditional on Type Baseline

**Bug:** mypy vetoes untyped codebases universally, causing false rejections.

**Fix:** Make g3 conditional: only active when the baseline codebase already has type annotations. If the baseline has zero mypy annotations, g3 is skipped (applicability rule from 3.3).

### 4.3 e5: Symbolic Verification Conditional

**Bug:** SymPy/z3 gate is non-executable without LLM intervention to determine which properties to verify.

**Fix:** Make e5 conditional with weight renormalisation. Only active when the fix contains mathematical claims (detected by AST analysis for sympy/z3 imports or numerical constants in assertions). When not applicable, e5 is skipped and weights renormalise.

## 5. Cell Type Architecture for Domain Generalisation

### 5.1 Core Concept

The CDSFL framework generalises across STEM domains by hosting specialist verification modules (cell types) that share a common protocol — exactly as biological organisms host specialised cell types within shared circulatory, immune, and nervous infrastructure.

### 5.2 Biological Mapping

| Biology | CDSFL |
|---------|-------|
| Organism | Framework (runner, brain, immune, endocrine, registry) |
| Cell types | Domain-specific verification modules |
| Circulatory system | Finding registry + message passing |
| Immune system | Quality filtering (domain-agnostic, operates on quality signals) |
| Brain | Convergence tracking (gamma/rho from any finding stream) |
| Endocrine | Health diagnostics (runs whatever checks active cell types define) |

### 5.3 What Each Cell Type Provides

```yaml
cell_type:
  domain: "<domain_name>"
  tool_mappings: [<tools>]
  hard_gates: [<gate_definitions>]
  effect_evidence: [<evidence_definitions>]
  fix_format: "<machine-readable format>"
  flaw_taxonomy: [<flaw_classes>]
  health_checks: [<endocrine_checks>]
```

### 5.4 Multi-Cell S_k Composition

When multiple cell types are active (e.g., software + mathematics for a SymPy module):

```
A = product over all active cell types of all hard gates
E = weighted aggregate over all active cell types of all effect evidence
S_k = A * E
```

Hard gate veto works ACROSS cell types. A code fix that parses (g_s1=1) but implements a dimensionally inconsistent equation (g_m1=0) gets S_k = 0.

### 5.5 Activation Routing

Hybrid approach:
1. **Explicit:** Task specification declares primary domain
2. **Implicit:** Content analysis detects secondary domains (e.g., SymPy imports activate maths cells)
3. **Immune system:** Evaluates quality signals regardless of which cell type produced a finding

Adding a new domain = write an expert encoding + register with composer. Runner, immune, brain, endocrine all work unchanged.

### 5.6 Tooling Maturity

The schema is complete. The tooling ecosystem is what may be incomplete. When a domain currently lacks tool-verifiable gates, ESCALATE is a development signal, not an architectural boundary. Domain experts build the missing tools for integration into the schema. Within STEM, every claim is in principle verifiable.

                       q: float, R: float) -> bool:

S* edge cases handled explicitly: nu_f=0 → S*=0 (any fix helps), nu_b=1 →

### 7.1 Test Articles

Items 4 and 5 are design proposals that the panel must converge on, not

optimal solutions for these architectural elements.

### 7.2 Composability Principle (HARD CONSTRAINT)

When multiple models propose different approaches to the same problem, the
default assumption is that they COMPOSE. The panel must demonstrate mutual
exclusivity before presenting any pair of proposals as an either/or choice.

Specifically:
- If Model A proposes approach X and Model B proposes approach Y, the first
  question is: does X + Y produce a better outcome than either alone?
- Only if combination is demonstrably worse than the best individual approach
  (not just equivalent — worse) may the proposals be treated as alternatives.
- "We propose X instead of Y" is not acceptable without showing that X + Y
  fails. "We propose X which subsumes Y" is acceptable if demonstrated.
- This applies to gate designs, encoding structures, activation strategies,
  enrichment methodologies, and all other architectural proposals.

All solutions must be optimal. The panel converges on the best combined
solution, not on a winner among competing proposals.

### 7.3 Sequential Burst Execution (HARD CONSTRAINT)

The panel processes each finding/problem **sequentially** — one at a time, not as
a single large batch. This is an execution constraint, not a suggestion.

**Burst Logic ITC Switching:** For each specific problem, use ITC switching to
cycle fresh model instances through each step. Each model receives a clean
context containing only the specific problem and the relevant source material.
This maximises attention gain on the individual problem and prevents cross-problem
contamination. "Switch them off and switch them back on again" for each unique
problem.

**Rationale:** Small focused problems converge faster than large problem sets.
ITC switching preserves error independence. A model that has been reasoning about
Problem 3 carries cognitive residue that may bias its judgment on Problem 4. Fresh
instances eliminate that residue.

**Final Integration Pass:** After all individual problems have been resolved, a
final pass presents the **full solution space** to the panel. All resolved fixes,
all converged designs, all updated artifacts — as a single integrated whole. The
panel evaluates whether everything ties together: are there emergent contradictions
between individually-correct solutions? Does the integrated whole satisfy all HARD
constraints simultaneously? This is where cross-cutting issues surface.

**UX Target:** This burst logic methodology is a candidate for user-selectable UX
options in the system. The execution pattern (sequential problem isolation →
burst ITC per problem → final integration) is domain-invariant and should be
available as a configurable execution mode.

## 11. Risk Assessment

### What Could Go Wrong

1. **SEARCH/REPLACE parser too strict:** Models may produce blocks that don't exactly match. Mitigation: fuzzy matching with confidence score, fall back to ESCALATE.

2. **Gate evaluation side effects:** Running pytest or mypy may modify state. Mitigation: evaluate in isolated temporary directory (copy source, apply fix, run gates, discard).

3. **S* threshold too high:** Conservative floor may reject all fixes. Mitigation: start with computed S* only (no floor) for Exp 38, calibrate floor from data.

4. **Self-referential bias:** Models reviewing their own framework may be systematically blind to certain failure modes. Mitigation: the five-model panel provides diversity; additionally, the mathematical model itself constrains the space of valid improvements.

5. **Combinatorial gate explosion:** Many gates from multiple cell types. Mitigation: only Python cells activate for Exp 38 (single domain). Multi-cell composition is tested in BR2.

### Explicitly Deferred to Phase B/C

The following items from the Codex implementation review (Exp 38 confer) are
acknowledged but intentionally deferred. They are not prerequisites for Exp 38:

1. **Dynamic expert encoding loader** — gates are hardcoded to Python for Exp 38.
   Multi-domain loader needed for Bench Run 2 (Phase C).
2. **Gate registry/dispatcher** — no plugin architecture. Static dispatch is
   sufficient for single-domain Exp 38. Dynamic dispatch needed for cell type
   architecture (Phase B).
3. **R_k persistence across rounds** — R_k is computed per-finding and stored on
   the registry entry, but not tracked round-over-round as a time series. Round-
   level R_k tracking is a Phase B enhancement for convergence analysis.
4. **Immune/brain/endocrine integration** — S_k pipeline is standalone; not yet
   wired to the immune (quality filter), brain (convergence), or endocrine
   (diagnostics) subsystems. Integration is Phase B architecture work.

The panel should NOT spend cycles rediscovering these gaps during Exp 38. They
are known, documented, and sequenced into the roadmap.
