## Item 1E.8 — Ouroboros query-quality fix

### State going in

The Ouroboros cell issues external research queries to arXiv and Semantic
Scholar to triangulate uncertain findings. The pre-1E.8 failure mode
(observed in Exp 39 shadow logs) was that queries contained literal finding
identifiers like `"uncertain finding Gemini_F002"` rather than the actual
description, so every arXiv query returned zero results and status
`shadow_mock`.

### Work

Audit of `bench/ouroboros_cell.py` showed the fix was already present in
the code, annotated with a "HARD FIX" comment:

- `_select_targets` (line 234) resolves finding IDs to descriptions via a
  `fid_to_desc` lookup from `round_findings`, emitting
  `uncertain_finding:<desc>` targets. Only when a description is missing
  does it fall back to the ID.
- `_target_to_query` (line 298) strips percentages, decimals, parenthetical
  detail, and the `uncertain_finding:` prefix, producing a clean keyword
  query.
- `_build_queries` (line 278) distributes targets across
  `allowed_sources` round-robin.

`arxiv` package 2.4.1 is installed and constructible. `bench/tests/test_ouroboros_query_quality.py` adds 12 tests covering the
four load-bearing contracts:

1. Description text appears in query, not finding ID (canonical
   acceptance test on the "Bayesian recursive self-assessment for LLM
   output" description).
2. Empty-description fallback to ID is safe.
3. Noise stripping: percentages, decimals, parentheticals removed;
   salient keywords preserved.
4. Source rotation across multiple targets hits multiple sources.

A `@pytest.mark.network` test hits the real arXiv API and confirms the
status is `live` or `live_empty` rather than `shadow_mock`.

**Result:** 12/12 pass (approximately 132 seconds wall-clock due to the
live network test).

## Item 1E.11 — OpenRouter function-calling tool-use mode

### Gap addressed

CC1 and CC2 have native Bash via the Claude CLI and can shell out to SymPy,
z3, pytest, ruff, and mypy directly. The other four panel models (Codex,
Gemini, ChatGPT, DeepSeek) reach the system via OpenRouter (or a dedicated
DeepSeek path) and have no tool execution unless the host wires structured
function calling.

### New module — `bench/openrouter_tools.py`

Key exports:

- **`TOOL_SPECS`** — five OpenAI function-calling JSON-schema specs:
  `sympy_verify`, `z3_verify`, `pytest_run`, `ruff_check`, `mypy_check`.
- **Subprocess-isolated local dispatchers** — `_run_sympy_verify` and
  `_run_z3_verify` defer to the immune-agent verifiers so the MF-40 AST
  blocklist and evidence format live in one place. The file-based
  dispatchers (`_run_pytest`, `_run_ruff`, `_run_mypy`) run the tool via
  `subprocess.run` with a bounded timeout and return a truncated
  stdout/stderr tail.
- **`_resolve_repo_path(path_str)`** — path-safety gatekeeper. Rejects
  absolute paths outside the repo, traversal escapes like
  `"../../../etc/passwd"`, and symlink escapes.
- **`dispatch_tool_call(name, arguments_json) → str`** — routes by tool
  name. Every failure mode returns JSON so the model can parse the
  response: unknown tool, malformed JSON arguments, missing required
  argument, handler exception.
- **`call_openrouter_with_tools(...)`** — the tool-call loop. The model
  emits `tool_calls`, the host executes each, the result is appended as a
  `role="tool"` message, and the conversation is re-sent until the model
  produces a final assistant message with no more `tool_calls` or the
  `MAX_TOOL_ITERATIONS` cap (6) is hit.

### Tests — `bench/tests/test_openrouter_tools.py`

36 tests covering:

- TOOL_SPECS structure (7 tests): five tools registered, every spec is
  `type=function`, every spec has the required function block, parameters
  are valid JSON-schema objects, names unique, every advertised name has
  a dispatcher registered, expected names present.
- `dispatch_tool_call` routing (7 tests): unknown tool, malformed
  arguments, missing required argument, empty arguments string, SymPy
  happy path, z3 happy path, handler exception surfaced as JSON error
  rather than raise.
- Path safety (5 tests): relative repo path accepted, absolute path
  outside rejected, traversal rejected, mixed-path traversal rejected,
  absolute-inside accepted.
- Filesystem-backed dispatchers (6 tests): missing-path rejection for
  pytest/ruff/mypy, ruff runs on a clean file, mypy runs on a typed file,
  pytest runs on an existing test node.
- Tool-call loop mocked against `openai.OpenAI` (8 tests): missing API
  key raises, single turn no tool calls, multi-turn single tool
  execution, chained two-tool calls across three iterations, max
  iterations cap enforced, empty choices surfaces as error, tools-None
  opt-out path, system prompt forwarded.
- Module constants (3 tests): `MAX_TOOL_ITERATIONS == 6`, `REPO_ROOT`
  points at project, timeout positive.

**Result:** 36/36 pass (approximately 11 seconds wall-clock).

## Item 1E.12 — DeepSeek R1 reasoner as formal-verification specialist

### Gap addressed

DeepSeek R1's long-reasoning chain-of-thought makes it well-suited for
formal-verification style claims that the mechanical verifiers (z3, SymPy)
cannot decide — natural-language logical implications, abstract proofs,
claims that lack crisp SMT grounding.

### New verifier — `_verify_deepseek_formal` in `bench/immune_agents.py`

- Calls the existing `bench.experiment_11_orchestrator.call_deepseek` path
  with `model_id = "deepseek-reasoner"`, `max_tokens = 4096`, `timeout = 120 s`,
  and a structured prompt requesting strict JSON output.
- Parses the JSON via `_parse_deepseek_formal_response`, which is tolerant
  of markdown code fences and leading prose but strict on the required
  fields.
- **Confidence capped at 0.5** (`_DEEPSEEK_SPECIALIST_CONFIDENCE_CAP`) so
  LLM verdicts cannot outrank mechanical proofs in any voting scheme.
- **Graceful degradation:** missing `DEEPSEEK_API_KEY`, network error,
  unparseable response, out-of-contract verdict string → all yield
  `UNCERTAIN` with descriptive evidence, never raise.
- **Role distinctness:** `tool_used = "deepseek_formal"` (not the bare
  `"deepseek"` used by the panel role) so downstream synthesis can tell
  specialist verdicts apart from panel findings.

### Tool manifest entry

`bench/cdsfl_registry/tool_manifest.toml`:

```toml
[tools.deepseek_formal]
description = "DeepSeek R1 reasoner as formal-verification specialist..."
verifier = "_verify_deepseek_formal"
needs_file = false
claim_types = ["logical", "mathematical"]
domain_hints = ["mathematics", "information_science", "cs_software"]
cost_class = "slow"
install_check = "import openai"
package_hint = "openai>=1.0"
```

### Domain TOML wiring

`bench/cdsfl_registry/domains/immune/mathematics.toml`:

```toml
logical = ["z3", "sympy", "deepseek_formal"]
```

The order is load-bearing: the specialist dispatch walks the list
left-to-right and the first definitive verdict wins, so DeepSeek is only
invoked when z3 AND SymPy both return `UNCERTAIN` — keeping API cost
bounded.

### Tests — `bench/tests/test_deepseek_specialist.py`

29 tests covering:

- Response parsing (9): plain JSON, fenced JSON, fenced without language
  tag, leading prose, empty, whitespace only, junk, array (must reject —
  dict only), malformed braces.
- Graceful degradation (5): missing API key, network error, unparseable
  response, missing verdict field, invalid verdict string coerced to
  UNCERTAIN.
- Happy path (5): CONFIRMED roundtrip, REJECTED roundtrip, confidence
  cap at 0.5 even if model claims 0.99, negative confidence clamped to
  zero, fenced response still parsed.
- Role distinctness (2): `tool_used == "deepseek_formal"` not
  `"deepseek"`, evidence namespaced `deepseek_formal:`.
- Manifest + domain integration (2): registered in manifest,
  mathematics.toml wires specialist after mechanical tools.
- Dispatch integration (2): specialist verdict enters pipeline when
  mechanical tools defer, mechanical CONFIRMED short-circuits before
  DeepSeek (cost control).
- Module constants (4): confidence cap is 0.5, max_tokens ≤ 8192,
  timeout bounded [30, 300] s, model id contains "reasoner".

**Result:** 29/29 pass (approximately 1 second wall-clock — all tests
mock the API call).

## Related spawn

A side discovery during 1E.11 sanity-checking: `_verify_sympy` in
`bench/immune_agents.py` returns UNCERTAIN on every claim (including
trivial identities like `x + 0 - x`) because its sandboxed subprocess uses
`global_dict={'__builtins__': {}}` which prevents SymPy from constructing
`Integer` literals during parsing. This is a silent framework-wide
regression — every SymPy specialist call currently returns UNCERTAIN in
the live pipeline regardless of claim truth. A separate background task
was spawned to address it without reopening the MF-40 RCE vector that the
current blocklist closes.
