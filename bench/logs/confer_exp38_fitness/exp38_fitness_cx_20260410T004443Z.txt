# 1. PARSE PATH

## FIND
Walkthrough of `parse_search_replace_blocks()`.

## FOLLOW
This feeds directly into `compute_sk()`. If parsing drops or mangles blocks, the fix is either rejected pre-gate or silently partially applied.

## ANALYSE
### Case (a): single file
**Works** for standard form:
```text
<<<< SEARCH bench/reference_runner.py
old
====
new
>>>> REPLACE
```
It:
- splits text into lines
- finds start if stripped line starts with `<<<<` and contains `SEARCH`
- strips off `SEARCH ` or `SEARCH\t`
- captures search until a bare `====`
- captures replace until line starts with `>>>>` and contains `REPLACE`

### Case (b): multiple files
**Parses correctly** as multiple `FixBlock`s. No state leak between blocks.

### Case (c): multi-line search/replace content
**Works**. Search and replace payloads are line-collected and `"\n".join(...)`.

### Case (d): content containing delimiter-like strings
This is where the parser is **strict, not robust**:
- A payload line equal to bare `====` **always terminates search**.
- A replace payload line beginning with `>>>>` and containing `REPLACE` **always terminates replace**.

So if the literal source being edited contains a line exactly `====`, or a line like `>>>> REPLACE marker`, parser cannot represent it.

The code comment claims delimiter-like content inside payloads does not break parsing, but that is only true for non-bare variants. Bare delimiter lines still break it.

## Self-falsification
Could this be irrelevant for Exp 38 because Python source rarely contains a bare `====` line? Mostly yes. But the question explicitly asks about delimiter-like strings, and the answer is that **bare delimiter lines break**. This is real but probably not a blocker for runner self-review.

## Result
### Surviving assessment
- **Not a go/no-go blocker by itself** for Exp 38’s target artifacts.
- But parser behavior is narrower than claimed.

### Matching logic

## Self-falsification

# 4. THRESHOLD PATH

## FIND
Walkthrough of `check_sk_threshold()` and `compute_rk()`.

## FOLLOW
Wrong math here means bad go/no-go decisions for fixes and bad stored residual risk.

## ANALYSE
### Nu clamping
Both functions clamp `nu_b`, `nu_f` to [0,1] and proportionally scale if sum > 1.

That part is fine.

### S\* computation
```python
s_star = (nu_b + nu_f - nu_b*nu_f - q*R) / (nu_f * (1 - nu_b))
```
Edge cases handled:
- `nu_f ≈ 0` => 0
- `nu_b ≈ 1` => 1
- final clamp to [0,1]

### Missing validation
Inputs `q`, `R`, and `sk` are not validated/clamped.
If registry entry has:
- `q < 0` or `q > 1`
- `R_old < 0` or `R_old > 1`
- `sk` outside [0,1] from corrupted entry

then math remains executable but semantics break.

Examples:
- `R_old = 2.0`, `q = 0.9` gives denominator `1 - q*R_old = -0.8`, so `R_det` becomes negative or inverted.
- `q = -1` increases risk oddly.
- `sk = 1.5` would over-weight `R_det`.

`compute_rk()` clamps only final `R_k`, masking invalid intermediate states.

This is a **silent incorrect result** risk.

## Self-falsification
Could Exp 38 supply only sane params? Probably by convention, yes. But `_evaluate_sk_for_findings()` reads:
```python
meta = entry.get("model_params", {})
nu_b = meta.get("nu_b", 0.05)
nu_f = meta.get("nu_f", 0.20)
q = meta.get("q", 0.5)
R_old = meta.get("R", 0.5)
```
No guarantee these are validated upstream in the shown code. Since the question asks about end-to-end clean execution, this remains a real boundary defect.

## Result
### Confirmed issue 3
**Risk/threshold math accepts invalid `q`, `R_old`, `sk` without validation, producing silently nonsensical outputs.**

# Answers to the seven explicit questions

## 1. PARSE PATH
- **(a) single file:** yes, standard block parses.
- **(b) multiple files:** yes, multiple blocks parse.
- **(c) multi-line search/replace:** yes.
- **(d) delimiter-like strings:** non-bare lookalikes are okay; **bare `====` inside SEARCH or a `>>>> ... REPLACE` line inside REPLACE breaks parsing**. Not likely blocker for Exp 38, but parser is stricter than claimed.

## 2. APPLY PATH
- **(a) trailing whitespace differences:** exact string match fails; fix rejected pre-gate.
- **(b) different file prefix:** exact full path or basename match only. Other prefixes skipped.
- **(c) multiple blocks same file:** applied in order to evolving modified text; later blocks must match post-edit content.

## 3. GATE PATH
- **g1 AST:** safe parse gate, returns 1/0.
- **g2 py_compile:** safe compile gate, returns 1/0, low-probability unhandled temp-file cleanup errors.
- **e2 regression:** real bug: unparseable/abnormal output can score 1.0.
- **e3 ruff:** real bug: tool failure/non-JSON can score as zero violations.
- **e4 bandit:** same as ruff.

## 4. THRESHOLD PATH
- Nu handling fine.
- S\* edge cases handled.
- **Invalid `q`, `R_old`, `sk` are not validated**, so mathematically nonsensical but non-crashing results are possible.

## 5. INTEGRATION PATH
- Findings selected by status plus `proposed_fix` containing `<<<< SEARCH`.
- Results stored under `entry["sk_result"]`.
- Logs emitted for admissible/rejected/escalate and round summary.
- In shown code, feedback is limited to registry/logging; not yet integrated into immune/brain/endocrine, as documented.

## 6. CONFIGURATION
Must set:
- `sk_enabled=True`
- `test_cmd` for e2 to be active/useful

Defaults that silently skip/degrade:
- `sk_enabled=False` disables entire pipeline
- `test_cmd=None` disables regression evidence
- provided `RunnerConfig` artifact may crash if missing `@dataclass`

## 7. CRASH SCENARIOS
Confirmed strongest:
- `RunnerConfig.from_dict()` if class lacks `@dataclass` → `AttributeError`
Possible:
- `_evaluate_sk_for_findings()` if entry lacks `"status"` → `KeyError`
- temp-file cleanup `os.unlink(...)` in finally blocks under filesystem anomaly → `OSError`
