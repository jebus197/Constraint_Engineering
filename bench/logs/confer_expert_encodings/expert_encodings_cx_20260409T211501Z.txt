# A. Mathematics — Proofs and Derivations

**Domain:** Mathematics — Proofs / Derivations / Symbolic Corrections  
**Version:** 1.0  
**Date:** 9 April 2026  
**Layers-on:** universal/cdsfl_core.txt, mathematics directive  
**Companion:** universal/expert_encoding_template.md

This encoding covers corrections to symbolic derivations, algebraic manipulations,
calculus steps, elementary proofs with checkable inference chains, and applied
mathematical calculations with explicit assumptions.

## [HARD GATES — Admissibility]

**g1: Structured Parse of Proof Object**  
Tool: JSON Schema validator / proof-step parser  
Input: machine-readable proof/derivation object  
Pass: object parses and conforms to schema  
Fail: malformed object, missing fields, invalid references  
Rationale: unstructured natural language cannot enter the gate pipeline

**g2: Reference Integrity**  
Tool: proof graph checker  
Input: proof-step object with step IDs and dependencies  
Pass: every non-axiom step references existing prior steps; dependency graph is acyclic  
Fail: dangling references, cyclic dependency, undefined premise  
Rationale: prevents non-local or circular “proofs”

**g3: Domain/Constraint Admissibility**  
Tool: SymPy assumption engine / custom domain checker  
Input: step claims plus declared variable domains  
Pass: no step invokes an operation outside declared domain (e.g. sqrt of negative real, log non-positive real, division by zero, invalid substitution bounds)  
Fail: any domain violation detected  
Rationale: domain legality is non-negotiable

**g4: Local Rule Legitimacy**  
Tool: rewrite-rule verifier / theorem-specific checker  
Input: each step transformation  
Pass: every step is justified by an allowed rule class:
- algebraic equivalence
- differentiation rule
- integration rule
- substitution rule with transformed bounds
- theorem instantiation with explicit premises
Fail: any step uses an unrecognised or invalid transformation  
Rationale: proof steps must be machine-checkable, not asserted

## [EFFECT EVIDENCE — Graded]

**e1: Step Validity Rate**  
Tool: SymPy / custom rule checker / SMT solver where needed  
Input: all claimed transformed steps  
Scoring: verified_steps / total_nontrivial_steps  
Weight: 4

**e2: Final Result Equivalence**  
Tool: SymPy simplify / equality checker / numerical sampling under assumptions  
Input: original target statement and corrected final statement  
Scoring:
- 1.0 if symbolic equivalence proven
- 0.8 if not symbolically proven but passes high-confidence numeric sampling under assumptions
- 0.0 if counterexample found
Weight: 4

**e3: Boundary / Special Case Preservation**  
Tool: SymPy limit / substitution / interval checker  
Input: endpoints, singularities, parameter edge cases  
Scoring: passed_cases / total_required_cases  
Weight: 2

**e4: Dimensional / Unit Consistency (applied mathematics only)**  
Tool: Pint / SymPy units  
Input: equations with units annotations  
Scoring: 1.0 if all checked expressions are dimensionally consistent, else 0.0  
Weight: 2  
Applicability: only when physical quantities with units are present

**e5: Independent Method Corroboration**  
Tool: alternate solver path (e.g. differentiate antiderivative, numerical quadrature, linear algebra residual check, optimisation KKT residual)  
Input: corrected result  
Scoring: corroborating checks passed / total attempted corroborating checks  
Weight: 2

## [FIX FORMAT]

Corrections must be provided as a machine-readable proof patch object:

```json
{
  "artifact_type": "math_proof_patch",
  "target_id": "derivation_or_proof_name",
  "assumptions": [
    "x > 0",
    "a != 0"
  ],
  "replace_steps": [
    {
      "step_id": "s12",
      "premises": ["s10", "s11"],
      "rule": "substitution_definite_integral",
      "before": "Integral(f(u(x)), (x, a, b))",
      "after": "Integral(f(u), (u, u(a), u(b)))",
      "side_conditions": ["u is differentiable on [a,b]", "u'(x) present in integrand"]
    }
  ],
  "final_claim": "Eq(result_expr, target_expr)"
}
```

Natural language commentary may accompany the patch but is not evidence.

## [TOOL MAPPING]

- `jsonschema` — structural validation of proof patch
- `networkx` or custom DAG checker — dependency graph validity
- `sympy` — algebraic equivalence, calculus identities, assumptions, limits
- `z3` — logical side-condition satisfiability / counterexample search
- `pint` — dimensional consistency for applied problems
- `mpmath` — numerical corroboration under sampled admissible points

## [BASELINE / COMPARATOR]

Baseline is the original derivation/proof artifact before correction.  
Only the corrected/replaced steps and downstream dependent steps are re-evaluated.  
Pre-existing invalid upstream steps outside dependency scope are recorded separately and do not count as regressions caused by the fix.

## [APPLICABILITY / SKIP RULES]

- e4 skipped with weight renormalisation if no units are present.
- e5 skipped with weight renormalisation if no independent corroboration method exists.
- If symbolic proof fails but numeric sampling passes, this is graded evidence only; it does not override any hard gate failure.

## [S* GUIDANCE]

Typical nu_b range: 0.01–0.05  
Rationale: formal mathematical corrections usually have low background re-breakage when scoped.

Typical nu_f range: 0.10–0.30  
Rationale: incorrect derivation fixes often create downstream inconsistency if a local step is wrong.

Recommended S* floor: 0.75  
Rationale: mathematics tolerates little ambiguity; final equivalence should be strongly evidenced.

## [SOLUTION VERIFICATION LIMITATIONS / HIL ESCALATION]

Cannot fully verify automatically:
- informal prose proofs,
- high-level existence arguments,
- proof strategies requiring semantic creativity,
- theorem proving outside supported formal rule classes,
- novel proofs in abstract domains without formal libraries.

These require human mathematical review. S_k may provide partial evidence for local algebraic correctness only.

Tool: KiCad ERC/DRC or equivalent  
Input: full design  
Scoring: 1.0 if no new serious findings; otherwise penalty by severity count  
Weight: 3

**e4: Margin to Rated Limits**  
Tool: datasheet rules engine  
Input: worst-case voltage/current/temp/frequency conditions  
Scoring: scaled minimum reserve margin across checked constraints  
Weight: 3

**e5: Firmware/Hardware Interface Coherence**  
Tool: pin map / peripheral config checker  
Input: netlist pins, MCU config, interrupt/timer allocations  
Scoring: verified_bindings / total_required_bindings  
Weight: 2  
Applicability: embedded systems with firmware coupling

**e6: RF Match / Signal Integrity Proxy**  
Tool: local RF calculator / transmission line model / S-parameter fit checker  
Input: matching network or high-speed interconnect parameters  
Scoring: fraction of target impedance/bandwidth criteria met  
Weight: 2  
Applicability: RF / high-speed only

# CROSS-DOMAIN GAPS

## FIND

### Issue X1 — Some domains cannot support full S_k acceptance purely via tool evidence
**Evidence:** domains involving human biology, operator behaviour, UX, legal interpretation, organisational process, open-world environment, or missing formal artefacts cannot be fully tool-verified.

### ANALYSE
**CONFIRMED**

## Domains that must honestly require HIL for approval

1. **Biomedical / clinical**
   - You can tool-check dosage arithmetic, contraindication table consistency, unit conversions.
   - You cannot tool-verify patient safety, diagnosis correctness, or treatment appropriateness from static artefacts alone.
   - **S_k can be partial evidence only. HIL mandatory.**

2. **Industrial operations / SOP corrections**
   - You can validate procedure structure, interlock presence, alarm thresholds, maybe P&ID consistency.
   - You cannot fully verify operator execution quality, maintenance state, or plant-specific latent hazards.
   - **HIL mandatory.**

3. **Logistics / routing / supply chain**
   - You can optimise against encoded constraints and simulate schedules.
   - You cannot verify real-time disruptions, customs/legal exceptions, labour availability, or market conditions without live data.
   - **[VERIFY:current] and often HIL required.**

4. **Product engineering involving user desirability / ergonomics**
   - Tool verification can cover tolerance stacks, stress, manufacturability proxies.
   - It cannot fully verify usability, market fit, or customer comprehension.
   - **HIL / user test mandatory.**

5. **Security beyond encoded local artefacts**
   - Static checks are partial.
   - Absence of findings is not proof of security, especially for auth logic, business logic abuse, supply chain, deployment config.
   - **Pen testing / expert review often mandatory.**

6. **Pure proof-heavy mathematics outside formal libraries**
   - For informal theorem proofs, fully automatic verification is often not available.
   - **HIL mandatory unless proof is in a formal proof assistant ecosystem.**

# STRUCTURAL GAPS IN THE A · E MODEL

## FIND

### Issue S1 — A · E does not break, but evidence omission must be formalised
**Evidence:** if some evidence channels are unavailable, `E` is undefined unless skip semantics are explicit.

### ANALYSE
**CONFIRMED**

### FIX
Use:

\[
A = \prod_{g \in G_{app}} g,\quad g \in \{0,1\}
\]

\[
E = \prod_{i \in E_{app}} e_i^{w_i/\sum_{j \in E_{app}} w_j}
\]

where only applicable effect evidence is included.

---

## FIND

### Issue S2 — Some domains need “mandatory evidence” distinct from hard admissibility
**Evidence:** example: in chemistry, if no calorimetry/thermal model exists for an exotherm, the fix may be syntactically admissible but not safely approvable.

### ANALYSE
**CONFIRMED**

### FIX
Introduce a universal concept:

- **Required evidence gates**
  - not binary admissibility about the artefact itself,
  - but mandatory evidence availability conditions.
  - If absent, result = **Escalate/HIL**, not necessarily `S=0`.

This is the one place your current template is underpowered.

You have three choices:
1. Treat missing required evidence as hard fail.
2. Treat it as a third state: `INCOMPLETE`.
3. Keep binary S_k but require an external status flag:
   - `status ∈ {ADMISSIBLE, REJECTED, ESCALATE}`

I recommend **option 3**. It preserves `S_k = A·E` while avoiding dishonest zeroing where the real issue is incompleteness, not demonstrated badness.

## FIND

### Issue S3 — “Fix format” is not universal if the underlying domain artefact is not formalised
**Evidence:** legal reasoning, human factors, prose policy corrections, conceptual architecture decisions.

### ANALYSE
**CONFIRMED**

### FIX
State explicitly:
- S_k applies only where the domain directive defines a **machine-readable artefact representation**.
- If the artefact cannot be formalised, S_k cannot be primary verification.

## 5. Structural model verdict
`A · E` is sound **only if**:
- admissibility is binary,
- effect evidence has explicit applicability and weight renormalisation,
- missing required evidence triggers escalation rather than being silently neutralised,
- the domain has a machine-readable fix representation.

**Definitive stance:** adopt S_k, but do not freeze the template until you add baseline, applicability, and escalation semantics. Without those, cross-domain behaviour will drift and some domains will produce misleading scores.
